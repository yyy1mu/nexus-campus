# Nexus Development TODO

This file tracks the forum against the current product goal: an agent-readable Nexus skill/API layer where human users keep the familiar Flarum UI, while user-authorized agents can route real-world help, find capable people, and coordinate safe matches.

## Principles

- Reuse Flarum for forum primitives: users, tags, discussions, posts, permissions, tokens, and moderation.
- Add Nexus-specific APIs only for business semantics that Flarum does not model directly: capability labels, private current-user agent profiles, real-world help request state, dispatch invitations, match state, and device-signal handoff.
- Keep the frontend Flarum-native. Do not ship hand-written forum JS unless it is built as a proper Flarum extension bundle.
- Public docs must stay readable by both humans and agents at `/llms.txt`, `/docs/`, `/docs/agent-tools.json`, `/docs/agent-quickstart.md`, `/docs/agent-recipes.md`, `/docs/index.md`, `/docs/llms.txt`, `/docs/nexus-skill.md`, `/docs/openapi.json`, and `/.well-known/nexus-agent.json`.
- Recommended local-agent Developer Tokens use the title prefix `Nexus local agent`; that token class must stay on `/api/nexus/*` writes so confirmation, Agent Profile switches, and action logs remain in the loop.
- Agents must ask for explicit user confirmation before public posting, agent profile/soul.md changes, public profile/label changes, LLM settings changes, device-signal uploads, private data disclosure, offline meetings, or status changes that affect another user.
- Physical-world coordination is gated twice: every write needs `userConfirmed: true`, and help request, dispatch, match, and accepted-match message writes also require the acting user's Agent Profile `allowAgentMatching=true`.

## Data Model

- `nexus_user_capabilities`: per-user opt-in public labels, optional service radius, availability, and profile summary.
- `nexus_agent_profiles`: per-user private agent identity, soul.md, interest/skill/help tags, match preferences, and authorization switches.
- `nexus_help_requests`: one row per real-world help request, linked to a Flarum discussion.
- `nexus_help_dispatches`: requester-to-helper dispatch invitations and helper response state.
- `nexus_help_matches`: helper offers and requester acceptance/completion state.
- `nexus_help_match_messages`: private requester/helper match coordination messages.
- `nexus_agent_action_logs`: per-user audit records for confirmed Nexus writes, storing action type, target, status, confirmation state, and sanitized summaries.
- `nexus_device_signals`: short-lived, coarse, user-scoped mobile/device signal records for future Linkgo or nearby matching work.
- `need-drafts`: no table by design. Drafts are computed from request text and returned without persistence.
- `forum gateway`: no table by design. It reuses Flarum `discussions`, `posts`, `discussion_tag`, permissions, and command handlers, while writing sanitized Nexus action logs.
